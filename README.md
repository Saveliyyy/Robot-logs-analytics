# Аналитика логов парка роботов

Учебный end-to-end проект аналитика данных: от «грязных» текстовых логов до витрины, SQL-аналитики, прогноза ошибок и Excel-отчёта, с ежедневным запуском в Airflow.

**Бизнес-вопрос:** какие роботы работают нештатно, почему, и кого завтра стоит отправить на обслуживание, не дожидаясь поломки в смену?

> Данные синтетические: их генерирует `generate_logs.py`, имитируя выгрузку из системы логирования (Loki). В них специально заложены дубли, битые строки, пропуски и мусор в показаниях датчиков, а один из роботов (R-03) постепенно начинает перегреваться.

## Стек

Python · pandas · NumPy · SQL (SQLite, запросы совместимы с PostgreSQL) · scikit-learn · matplotlib · Excel (openpyxl) · Apache Airflow · Docker

## Результаты

**ETL** — 551 тыс. строк за 60 дней по 4 роботам:

| Проблема в данных | Строк | Что сделано |
| --- | ---: | --- |
| Дубли (повторная отправка) | 10 961 | удалены |
| Битые строки | 2 682 | отброшены, учтены в отчёте качества |
| Мусор в температуре | 1 619 | заменены последним валидным значением |
| Пропуски заряда | 5 197 | заполнены `ffill` внутри робота |
| **Чистых строк** | **537 646** | загружены в БД, построена витрина |

**SQL-аналитика:**
- у R-03 доля ошибок 2,5% против 0,4% у остальных — единственный робот выше среднего по парку;
- при температуре ≥ 48 °C ошибок в 10 раз больше, чем при < 44 °C (4,1% против 0,4%);
- у R-03 с 17.08 непрерывная серия из 44 дней с максимальной температурой ≥ 50 °C;
- составной индекс ускорил поиск ошибок перегрева робота в 9 раз (`SCAN` → `SEARCH USING INDEX`).

**Прогноз ошибок на следующий день** (Ridge-регрессия, проверка на отложенных 14 днях):

| Метод | MAE, ошибок/день |
| --- | ---: |
| Модель (Ridge) | **5,05** |
| Наивный: «как неделю назад» | 6,38 |
| Наивный: «как вчера» | 8,46 |

Модель точнее лучшего наивного прогноза на 21% и на завтра помечает R-03 как кандидата на обслуживание.

## Структура

```
robot-logs-analytics/
├── generate_logs.py      # генерация «сырых» логов с типичными проблемами
├── etl.py                # extract → transform (pandas) → load (SQLite), витрина, проверка качества
├── sql/analysis.sql      # 8 запросов: LAG, ROW_NUMBER, RANK, скользящие окна, CTE, подзапросы, gaps & islands
├── run_sql.py            # выполняет запросы + демонстрация оптимизации через индекс и EXPLAIN
├── forecast.py           # прогноз ошибок: признаки, TimeSeriesSplit, сравнение с наивными моделями
├── report_excel.py       # Excel-отчёт: сводка на формулах, быстрый поиск, график, качество ETL
├── run_all.py            # весь пайплайн одной командой
├── dags/robot_logs_dag.py  # DAG Airflow: ежедневный запуск в 06:00
├── docker-compose.yml    # Airflow в Docker для локального запуска
└── output/               # результаты: CSV запросов, прогноз, график, Excel
```

## Как запустить

```bash
python -m venv .venv
.venv\Scripts\activate          # Windows;  на macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
python run_all.py               # ~30 секунд
```

Шаги можно запускать и по отдельности: `python etl.py --date 2026-08-15` обработает один день, повторный запуск не создаст дублей.

**Airflow:**

```bash
python generate_logs.py         # сначала сгенерировать логи
docker compose up               # интерфейс на http://localhost:8080
```

В интерфейсе включите DAG `robot_logs_daily` и запустите его вручную с нужной датой или сделайте backfill за период (команда в шапке DAG-файла).

## Что внутри и зачем

**ETL (`etl.py`).** Строки разбираются регулярным выражением через `str.extract` сразу для всего дня, без циклов. Загрузка идемпотентна: перед записью день удаляется, поэтому перезапуск безопасен. После загрузки `check_quality` проверяет число строк и долю битых записей и роняет задачу, если что-то не так: в Airflow это видно сразу.

**SQL (`sql/analysis.sql`).** Каждый запрос отвечает на конкретный вопрос: динамика ошибок к прошлому дню, скользящее среднее за 7 дней, топ-3 худших дня у каждого робота, роботы хуже среднего по парку, структура кодов ошибок, связь ошибок с температурой, тренд неделя к неделе, поиск непрерывных серий перегрева.

**Прогноз (`forecast.py`).** Все признаки строятся только из прошлого (`shift`), валидация через `TimeSeriesSplit`, итоговая проверка на последних 14 днях, которые модель не видела. Модель сравнивается с наивными прогнозами: без такого сравнения нельзя сказать, приносит ли ML пользу.

**Excel (`output/robot_report.xlsx`).** Лист «Сводка» считается формулами СУММЕСЛИМН, СРЗНАЧЕСЛИМН и МАКСЕСЛИМН: меняете даты периода в жёлтых ячейках, и сводка пересчитывается. Ниже — быстрый поиск ошибок робота за день через ИНДЕКС + ПОИСКПОЗ по двум условиям.

Упражнение: на листе «Данные» постройте сводную таблицу «робот × неделя → сумма ошибок» и добавьте срез по роботу.

## Что можно улучшить

- Заменить SQLite на PostgreSQL или ClickHouse и подключаться через SQLAlchemy.
- Добавить в прогноз внешние признаки: график смен, плановое обслуживание.
- Отправлять уведомление в Telegram, когда модель рекомендует обслуживание.
- Собрать дашборд в Grafana поверх витрины `daily_robot_metrics`.
